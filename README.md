# Call_me_Maybe

## Description

Call_me_Maybe is a project developed as part of the 42 curriculum. Its main goal is to create a function calling tool using an LLM.

The project focuses on constrained decoding, a technique used to control the output generated by manipulating unwanted token's logits.

The implementation aims to get a set of functions with information such as their name, description, parameter names and types and return type attatched to them and a set of prompts. The program will then output a json file containing each prompt and the function chosen with the values assigned to each parameter.

This project explores how constrained decoding can improve accuracy, reliability and the overall speed of the tool by doing some of the work instead of letting the prompt and context do the heavy-lifting.

## Algorithm Explanation
### Overview

This project uses constrained decoding for increased precision and reliability given that we are using a very light model (0.6B parameters).

Unlike standard decoding, which selects tokens based primarily on their probability, constrained decoding restricts the possible outputs according to a set of predefined rules or constraints.

### Algorithm Workflow

Input processing: The inputs are parsed from the corresponding json files and stored in memory to be used as context for our model.

Token selection: After we get all the information for the functions and the prompts, we start generating our answers.

- Limiting the model to tokens found in function names:
    - For the part where we get the model to choose a function, we limit the valid tokens to the ones found in every function's name and then pick the function with the highest logit average.

- Limiting the model to numbers:
    - When getting the parameters for the function, in case the parameter is a number, we limit the model to choosing numbers.

- For text parameters we do normal decoding instead of constrained decoding, to improve the model's precision we give it a good context and hope for the best.

Output generation: Generating the output was pretty straightforward, a class waas made to hold all the relevant information about the answers and we used a function that formats the output to a string and then write it to the assigned output file.

## Challenges Faced

During development, some challenges were encountered:

Challenge 1 - Determining when the model has finished it's answer

Problem: There is no magic word that determines the end of an answer, and if you keep asking the model for the next word, it will keep giving you more words.

Solution: The solution for this problem depends on the phase of the execution we are in. For the function choosing part, we do not predict the most likely next word, instead, we choose only one function with the highest average logit value and move on to the next prompt. For the parameter generation part, we give the model a "follow up" to the prompt, this follow up ends with an unclosed quotation mark, this way, whenever the model writes a quotation mark, it means that the generation for that parameter has ended and we can move on to the next one.

Challenge 2 - Not overconstraining \ underconstraining the model.

Problem: In some cases, constraining the model to too few tokens will lower it's precision and maybe even performance, the same goes for underconstraining, of course.

Solution: I believe this problem is never truly solved, there is always room for improvement in this matter.
